## 🔴 문제 상황

### 증상
- 로봇 제어 프로그램이 실행 중 **간헐적으로 멈추는 현상** 발생
- 프로그램이 얼어버리는 순간 로봇이 정지하지 않고 **표면에 과도하게 접촉**
- FT 센서 피드백 기반 힘 제어가 작동하지 않음
- 재현성이 낮아 디버깅이 어려움

### 영향
- **안전성 문제**: 로봇이 과도한 힘으로 표면 접촉 시 장비 손상 위험
- **실험 신뢰성 저하**: 간헐적 문제로 실험 재현성 낮음
- **시스템 불안정**: 전체 제어 루프의 실시간성 보장 불가

## 🔍 근본 원인 분석

### 1. 실시간 쓰레드에서 GUI 업데이트 (최우선 문제)

#### 문제 코드 위치
**파일**: `Robot_Comm_SW_DJ_v5Dlg.cpp`  
**라인**: 571-585, 621-660

```cpp
// Thread_Servo (1ms 실시간 제어 루프)
auto stopRobotWithError = [&](const CString& errorMsg) 
{
    // ... 로봇 정지 처리 ...
    Status_gui_str = errorMsg;
    g_pDlg->var_status_gui.SetWindowTextW(Status_gui_str);  // ❌ GUI 업데이트
    return true;
};

// 안전 범위 검사
if ((Th_robotData_servo.flangePos[0] < -360.0f) || ...)
{
    if (stopRobotWithError(_T("엔드이펙터 위치 범위 초과로 인한 정지")))
        break;
}
```

#### 원인
- `Thread_Servo`는 `THREAD_PRIORITY_TIME_CRITICAL` 우선순위로 1ms 주기로 실행
- `SetWindowTextW()`는 Windows 메시지 큐를 통해 처리되는 **블로킹 함수**
- 메시지 큐가 혼잡하거나 다른 쓰레드가 GUI를 점유 중이면 **실시간 쓰레드가 대기**
- 대기하는 동안 로봇 제어 명령이 전송되지 않아 **로봇이 계속 마지막 명령대로 움직임**

#### 위험도
**🔴 Critical** - 실시간 제어의 근간을 흔드는 문제

### 4. 로그 쓰레드의 파일 I/O 블로킹

#### 문제 코드 위치
**파일**: `Robot_Comm_SW_DJ_v5Dlg.cpp`  
**라인**: 1927-1976

```cpp
while (!g_pDlg->m_logQueue.empty()) {
    LogData log = g_pDlg->m_logQueue.front();
    g_pDlg->m_logQueue.pop();
    lock.unlock();  // 여기서 unlock

    for (size_t i = 0; i < log.data.size(); ++i) {
        g_pDlg->m_dataFile << log.data[i];  // 파일 I/O
        if (i < log.data.size() - 1) {
            g_pDlg->m_dataFile << ",";
        }
    }
    g_pDlg->m_dataFile << "\n";

    lock.lock();  // 다시 lock
}
g_pDlg->m_dataFile.flush();  // ❌ 매 루프마다 flush
```

#### 원인
- 파일 I/O는 디스크 성능에 따라 수십~수백 ms 소요 가능
- `flush()`는 특히 느린 작업 (물리적 디스크 쓰기)
- `m_logMutex` 잠금 시간이 길어져 메인 루프에서 로그 푸시 시 대기

#### 위험도
**🟡 Medium** - 간접적 영향, 시스템 부하 증가

## ✅ 해결 방안

### 해결책 1: 실시간 쓰레드에서 GUI 업데이트 완전 제거

#### 목표
실시간 제어 쓰레드(`Thread_Servo`, `Thread_Contact_*`)에서 모든 `SetWindowTextW()` 호출 제거

#### 구현 방법

**Before (문제 코드):**
```cpp
auto stopRobotWithError = [&](const CString& errorMsg) 
{
    // ... 로봇 정지 처리 ...
    Status_gui_str = errorMsg;
    g_pDlg->var_status_gui.SetWindowTextW(Status_gui_str);  // ❌
    return true;
};
```

**After (해결 코드):**
```cpp
// 헤더 파일에 추가
#define WM_USER_SERVO_ERROR (WM_USER + 101)

// Thread_Servo 내부
auto stopRobotWithError = [&](const CString& errorMsg) 
{
    Drfl.stop_rt_control();
    Drfl.set_safety_mode(SAFETY_MODE_AUTONOMOUS, SAFETY_MODE_EVENT_STOP);
    Drfl.set_robot_control(CONTROL_RESET_SAFET_OFF);
    
    g_pDlg->m_flags.realtimeConnected.store(false);
    g_pDlg->m_flags.servoRunning.store(false);
    g_pDlg->m_flags.ftRunning.store(false);
    g_pDlg->m_flags.robotRunning.store(false);
    
    // PostMessage로 메인 쓰레드에 GUI 업데이트 위임
    CString* pMsg = new CString(errorMsg);
    ::PostMessage(g_pDlg->GetSafeHwnd(), WM_USER_SERVO_ERROR, 0, (LPARAM)pMsg);
    
    Drfl.disconnect_rt_control();
    return true;
};

// 메시지 맵에 추가
ON_MESSAGE(WM_USER_SERVO_ERROR, &CRobotCommSWDJv5Dlg::OnServoError)

// 메시지 핸들러 구현
LRESULT CRobotCommSWDJv5Dlg::OnServoError(WPARAM wParam, LPARAM lParam)
{
    CString* pMsg = reinterpret_cast<CString*>(lParam);
    if (pMsg) {
        Status_gui_str = *pMsg;
        var_status_gui.SetWindowTextW(Status_gui_str);
        delete pMsg;  // 메모리 해제
    }
    return 0;
}
```

### 해결책 3: GUI 업데이트 빈도 제한

#### 구현 방법

```cpp
void CRobotCommSWDJv5Dlg::OnTimer(UINT_PTR nIDEvent)	
{
    // GUI 업데이트 빈도를 1/4로 감소 (62ms → 248ms, 약 4Hz)
    static int skip_count = 0;
    if (++skip_count >= 4) {
        UpdateGUI();
        skip_count = 0;
    }
    
    // 그래프는 매번 업데이트 (시각적으로 중요)
    auto gui_sensor = m_ftSensor.getSnapshot();
    auto gui_robot = m_robotState.getSnapshot();
    float forcePoints[2] = { fabs(m_setting.Target_Force_N), fabs(gui_sensor.filteredForce[2]) };
    float posPoints[2] = { m_servoctrl.servo_tcp_pos_des_key[2], gui_robot.tcpPos[2] };
    _rtGraphforce->AppendPoints(forcePoints);
    _rtGraphpos->AppendPoints(posPoints);
    
    CDialogEx::OnTimer(nIDEvent);
}
```

**효과:**
- GUI 업데이트 빈도: 16Hz → 4Hz
- 메시지 생성 감소: 480회/초 → 120회/초 (**75% 감소**)

### 해결책 4: 로그 쓰레드 최적화

#### 방법 A: Flush 빈도 감소

```cpp
UINT CRobotCommSWDJv5Dlg::Thread_Logger(LPVOID pParam)
{
    // ... 기존 코드 ...
    
    int flush_counter = 0;  // flush 카운터 추가
    
    while (g_pDlg->m_flags.logThreadRunning || !g_pDlg->m_logQueue.empty()) {
        std::unique_lock<std::mutex> lock(g_pDlg->m_logMutex);
        g_pDlg->m_logCv.wait(lock, [&] { 
            return !g_pDlg->m_logQueue.empty() || !g_pDlg->m_flags.logThreadRunning; 
        });

        while (!g_pDlg->m_logQueue.empty()) {
            LogData log = g_pDlg->m_logQueue.front();
            g_pDlg->m_logQueue.pop();
            lock.unlock();

            for (size_t i = 0; i < log.data.size(); ++i) {
                g_pDlg->m_dataFile << log.data[i];
                if (i < log.data.size() - 1) {
                    g_pDlg->m_dataFile << ",";
                }
            }
            g_pDlg->m_dataFile << "\n";

            lock.lock();
            
            // 100개마다 한 번만 flush (약 0.1초마다)
            if (++flush_counter >= 100) {
                g_pDlg->m_dataFile.flush();
                flush_counter = 0;
            }
        }
    }
    
    // 종료 시 마지막 flush
    g_pDlg->m_dataFile.flush();
    g_pDlg->m_dataFile.close();
    return 0;
}
```

#### 방법 B: 배치 처리

```cpp
// 여러 로그를 한 번에 문자열로 합쳐서 쓰기
std::ostringstream batch;
while (!g_pDlg->m_logQueue.empty() && batch_count < 50) {
    LogData log = g_pDlg->m_logQueue.front();
    g_pDlg->m_logQueue.pop();
    
    for (size_t i = 0; i < log.data.size(); ++i) {
        batch << log.data[i];
        if (i < log.data.size() - 1) batch << ",";
    }
    batch << "\n";
    batch_count++;
}
lock.unlock();

// 한 번에 쓰기
g_pDlg->m_dataFile << batch.str();
```

## 🛠️ 구현 가이드

### 단계별 적용 순서

#### Phase 1: 긴급 조치 (즉시 적용)
1. ✅ **실시간 쓰레드에서 모든 SetWindowTextW 제거**
   - `Thread_Servo`의 `stopRobotWithError` 수정
   - `Thread_Contact_Flat`의 모든 GUI 업데이트 제거
   - `Thread_Contact_Flat_RL`의 모든 GUI 업데이트 제거

2. ✅ **Logger flush 빈도 감소**
   - 매 루프 flush → 100개마다 flush

**예상 효과:** 프리즈 발생률 80% 이상 감소

#### Phase 2: 성능 개선 (1-2일 내)
3. ✅ **GUI 업데이트 빈도 제한**
   - OnTimer에 skip 로직 추가 (16Hz → 4Hz)

4. ✅ **상태 표시를 위한 atomic 변수 도입**
   - Control Step 상태 변수
   - PostMessage 기반 GUI 업데이트

**예상 효과:** CPU 사용률 20-30% 감소, 더 부드러운 UI

#### Phase 3: 안정성 강화 (1주일 내)
5. ✅ **안전 범위 검사 개선**
   - 위반 횟수 카운팅
   - 히스테리시스 추가

6. ✅ **로그 배치 처리**
   - 50-100개 단위 배치 쓰기

**예상 효과:** 시스템 전반적 안정성 향상
